# Conformance

The Work Verification Protocol's conformance corpus is the measure of this
implementation: packages produced by another implementation, each with the
outcome every verifier must reach.

## Where the corpus is

The corpus is published in [`dekrops/wvp`](https://github.com/dekrops/wvp),
with the specifications ([publication review](../docs/protocol/publication-review.md)).
Its specifications are licensed under CC BY 4.0, its vectors and examples
under Apache-2.0. This directory holds no fixtures; the tests that need them
read them from a path you supply.

## Running against the corpus

With a checkout of `dekrops/wvp` (or of `dekrops/verified`, where the corpus
is generated; the paths are the same):

```sh
VERIFIED_CONFORMANCE_DIR=/path/to/wvp/test-vectors \
VERIFIED_CONFORMANCE_REQUIRED=1 \
  cargo test --workspace --locked -- --nocapture
```

- `VERIFIED_CONFORMANCE_DIR` is the directory containing
  `canonical-hash-v1.json`, `wvp/`, `work-contract/`, `work-unit/`,
  `evidence-statement/` and `claim-registration/`.
- Without it the corpus tests print `skipped` and pass. With
  `VERIFIED_CONFORMANCE_REQUIRED=1` a missing corpus is a failure, so a run
  that claims conformance cannot skip silently.

Six test files use it:

| Test | Corpus | What it checks |
| --- | --- | --- |
| `verified-canonical/tests/shared_vectors.rs` | `canonical-hash-v1.json` | Canonical bytes and SHA-256 of every valid case; refusal of every invalid case. |
| `verified-contract/tests/conformance.rs` | `work-contract/v1` | The whole expected result of every case: decision, requirement values, ignored records, conflicts, or the refusal. |
| `verified-work-unit/tests/work_unit.rs` | `work-unit/v1/vectors.json`, `claim-registration/v1/unit.json` | Every key commitment, canonical identity and nullifier; the outcome of every unit check. |
| `verified-verifier/tests/evidence_conformance.rs` | `evidence-statement/v1` | The refusal code of every refused statement, chain and admission; the key, canonical text and digests of every accepted statement; the summary of every accepted chain; the evidence manifest of every accepted admission. Not the platform's verification result. |
| `verified-verifier/tests/registration_conformance.rs` | `claim-registration/v1/vectors.json`, `log.json` | The refusal code of every refused registration, and every stated fact of every accepted one. For logs: the refusal code, the segment's summary, or how the held entry relates to it. |
| `verified-verifier/tests/conformance.rs` | `wvp/v0.1`, `wvp/v0.2`, `expectations.json`, the worked examples | The whole expected report or refusal of every vector, under the registry the vector supplies. |

## In CI

The `conformance` job of [`ci.yml`](../.github/workflows/ci.yml) runs exactly
the command above on every pull request, against `dekrops/wvp` at the commit
the workflow names. To follow a new publication of the corpus, change that
commit and the results in
[`docs/protocol/compatibility.md`](../docs/protocol/compatibility.md) in one
pull request.

Part of the corpus has no test here yet and is not counted: of
`claim-registration/v1`, `vectors.json` (registrations), `log.json` (log
segments and held entries) and `unit.json` (unit checks) are run;
`audit.json`, `notice.json` and `dispute.json` are not.

## Synthetic examples are something else

[`examples/`](../examples/) holds checked-in synthetic packages for trying the
tool and testing integrations. They are generated by this project, so agreeing
with them says nothing about conformance.

## Rules

- Expected outcomes come from the vectors. If this implementation disagrees
  with one, the specification is investigated; the expectation is never edited
  to make a test pass.
- A vector this implementation cannot run is named in the test's output and
  in [`docs/protocol/compatibility.md`](../docs/protocol/compatibility.md).
  It is never counted as conforming.
- Tests in this repository that do not need the corpus build their packages in
  process (`crates/verified-verifier/tests/support`). That data is synthetic,
  signed with throwaway keys derived from fixed seeds, and is not protocol
  test material.
